\section{Introduction}
\label{sec:intro}

This is the second co-design and energy-efficiency report of the dealii-X project.
It is a direct continuation of Deliverable D3.2, \emph{Co-Design and Energy Efficiency Report~I}.
The motivation for the work, the selection of the CEED Bake-off Kernels (BK) and Bake-off Problems (BP) \citep{Fischer20scalability} and the streaming kernels \citep{Chalmers20} as proxies for the algorithmic core of high-order finite element codes, and the description of the benchmark repository\footnote{\url{https://github.com/dealii-X/benchmarks/}} are given in D3.2 and are not repeated here.

D3.2 established a performance baseline for the scalar operator-evaluation kernels BK1, BK3 and BK5 on NVIDIA, AMD and Intel accelerators, using a range of programming models (CUDA, Kokkos, OpenCL, OpenMP target offloading and the Tiny Tensor Compiler), together with an initial characterization of the streaming kernels on CPUs.
It closed by identifying three directions for the remaining project period: the exploitation of matrix instructions and cross-element vectorization, the extension from isolated operator evaluation to the complete solver chain including multigrid preconditioners, and the adoption of a portable, process-based methodology for energy measurement.
Here we report on the outcome of those three directions.

Since D3.2, the performance optimization effort has concentrated on three new areas:

\begin{itemize}
    \item \textbf{Batched (thread-coarsened) kernels.}
    The single-element-per-thread-block mapping used in D3.2 leaves registers, shared memory and -- on AMD hardware -- the wavefront underutilized at low polynomial order.
    Assigning several elements to each thread block removes this limitation and yields a $2\times$ speedup for $p=1$ on the NVIDIA GH200 (Section~\ref{sec:codesign}).
    This directly addresses the poor low-order performance that was observed but left unresolved in D3.2.
    \item \textbf{Raviart--Thomas vector element kernels.}
    The kernels studied in D3.2 were exclusively $H^1$-conforming and scalar-valued.
    Mixed formulations of the Navier--Stokes equations instead require $H(\mathrm{div})$-conformity, and we therefore extend the benchmark suite with the vector mass, mixed divergence and mixed gradient operators of the Raviart--Thomas element family.
    \item \textbf{Full Bake-off Problems including solvers and preconditioners.}
    Operator evaluation is embedded in a conjugate gradient solver and in multigrid-preconditioned solvers within the deal.II framework, so that gather--scatter overheads, inter-GPU communication and preconditioner cost enter the measurement.
    This closes the gap between the BK and BP figures of merit that was left open in D3.2.
\end{itemize}

Where D3.2 could only outline the process-based measurement strategy of \citet{Cielo25}, this report presents measurements obtained with the \texttt{p3em} energy meter and an explanation of the energy efficiency metrics.

\subsection{Purpose of the Document}

The purpose of this document is to report the co-design outcomes of Work Package~3 in the second half of the project: which implementation techniques were found to reach hardware limits on current accelerators, which programming models are mature enough to be relied upon, and what the associated energy cost is.
The findings are intended to inform the library developments in WP1 and the application developments in WP2, as well as the wider finite element and GPU computing communities.

The performance-portability objectives stated in D3.2 remain unchanged: programs should deliver good performance across diverse computing architectures while requiring only minor platform- and simulation-specific tuning.

\section{{Co-design for High-Performance Finite Element Kernels}}
\label{sec:codesign}

We detail the implementation techniques and performance measurements of high-order matrix-free finite element methods on modern graphics processing units (GPUs).
The matrix-free framework and its initial implementations are described in Deliverable 1.3 (\url{https://github.com/dealii-X/deliverables/blob/main/D1.3/D1.3_dealii_report.pdf}).
To evaluate these problems, we adopt the bake-off benchmarks \cite{Fischer20scalability} as our baseline problems. In this report, we also implement a new technique to improve operator performance for low-order elements.

\subsection{Batched Operator Evaluation}

Previous high-order matrix-free GPU implementations were based on assigning a single element per thread block \cite{tens_prod}. This approach causes low-order elements to underutilize
the streaming multiprocessors (SMs) because NVIDIA only allows each SM to schedule 32 thread blocks \cite{nvidia_hopper_tuning}. Consequently, low-order elements reach this limit,
leaving registers and shared memory underutilized within each SM. On AMD GPUs, the single element per thread block approach leaves the 64-thread wavefront underutilized for low-order elements, consequently causing poor performance.
Based on a batch processing approach, our technique assigns multiple elements to each thread block to overcome these limitations. For example, a polynomial order of 1 in the Laplace operator evaluation (Bake-off Kernel 3 in the CEED benchmarks) can fit 11 elements per thread block.
A performance comparison between the single-element-per-thread-block and the batched processing approaches is given in Figure~\ref{fig:BK3_1_10}. The new technique achieves a 2$\times$ speedup for polynomial order 1 on the NVIDIA GH200 Superchip at the JUPITER supercomputer located at the Jülich Research Centre.
New batched implementations are available at \url{https://github.com/dealii-X/benchmarks/tree/main/CEED\_BK}.

\subsection{Experimental Setup}

Performance analysis and benchmarks were conducted on the NVIDIA Grace Hopper Superchip (GH200) on the JUPITER supercomputer and on the AMD MI250X GPU on the LUMI supercomputer. The Kokkos performance portability layer
v5.1 \cite{kokkos} was used to target traditional compute cores. For tensor core implementations, CUDA PTX mma instructions v9.3 \cite{nvidia_mma} were employed.

\subsection{Laplace Solver Performance (CEED BP3)}
We extend our operator evaluation to a complete linear solver by embedding the Laplace operator within a Conjugate Gradient (CG) method, corresponding to the CEED Bake-off Problem 3 (BP3) benchmark.
The solver, implemented within the deal.II finite element library framework is evaluated on both single and multi-GPU configurations of the NVIDIA GH200 Superchip, utilizing MPI with peer-to-peer (P2P) communication enabled. Figure~\ref{fig:BK_BP} illustrates the initial performance results,
highlighting that the performance difference between operator evaluations (BK) and full linear solvers (BP)
is primarily driven by gather-scatter overheads and inter-GPU communication. Additionally, the results confirm the computational efficiency of high-order elements which directly leverage the tensor-product formulation of the shape functions to increase arithmetic intensity.
The source code can be found at \url{https://github.com/dealii-X/benchmarks/tree/main/CEED_bp}.

\subsection{Raviart-Thomas Elements and Kernel Performance}

$H^1$-conforming elements (as used in the CEED Bake-off kernels) enforce continuity of all vector components across elements, whereas the Navier-Stokes equations, in mixed formulations often require continuity of the normal component of the flux across element boundaries which is a property of $H(\mathrm{div})$-conforming spaces.
Elements designed for this purpose are known as Raviart-Thomas finite elements.
We implement the vector mass, mixed divergence and mixed gradient operators -- the core operations in Raviart-Thomas kernel design -- in our benchmarks repository: \url{https://github.com/dealii-X/benchmarks/tree/main/rt\_kernels}.

Figure\ref{fig:GH200_vector_Mass} shows the performance of the vector Mass operator on the NVIDIA GH200 in both FP32 and FP64 precisions.
Batch processing enabled all polynomial orders to achieve similar throughput (GDoF/s).
Similar trends are observed for the AMD MI250X GPU from the LUMI supercomputer, which performs well given its $1.3\text{ TB/s}$ STREAM bandwidth.
Only polynomial order 8 performs significantly worse than the other orders, as shown in Figure~\ref{fig:MI250x_vector_Mass}.
This drop in performance is likely due to register file capacity constraints in this slightly older AMD architecture.

\subsection{Alternative Programming Models}
\label{sec:progmodels}

The survey of GPU programming models begun in D3.2 has continued in support of the Work Package~1 developments, the aim being that the library implementations exploit accelerators from all three major vendors.
The main effort in this period went into optimizing kernels on Intel hardware with the Tiny Tensor Compiler, left as an open problem in the first report.

The model comparison of D3.2 has by now settled into a consistent picture.
OpenMP target offloading performs adequately at low polynomial orders but struggles with the arithmetically intensive kernels, offering too little control over shared memory allocation and register pressure.
OpenCL matches Kokkos; its drawback is uneven vendor support, NVIDIA profiling tools in particular lacking native OpenCL support, which complicates the analysis reported in Section~\ref{sec:codesign}.
High-level abstractions thus remain convenient for simpler workloads but lack the granularity to approach machine limits in high-order finite element computations, while among the lower-level portable models the deciding factor is less raw performance than the maturity of the surrounding tooling.

\subsubsection{Tiny Tensor Compiler: Status Update}

TinyTC, its tensor language and its execution model are described in D3.2, Section~2.4, with a complete Tensor IR listing of the prototype BK1 kernel.
There, the TinyTC implementation of BK1 reached about 10~GDoF/s on the Intel Data Center GPU Max (Ponte Vecchio) -- a quarter of the OpenMP throughput -- and dimension fusion alone gained only a few percent.
In consultation with the compiler author we concluded that index fusion, batch vectorization and memory layout transformations would be needed for satisfactory register and SIMD utilization on that architecture.

That strategy has since been implemented and the kernel set extended from BK1 to BK5.

Both kernels now run close to the achievable machine bandwidth of the target Intel GPUs.
Performance is sustained across a broad range of polynomial orders, unlike the OpenMP implementations noted above; the residual loss at very high orders is a tuning rather than a structural problem, attributable to shared local memory allocation and padding.

TinyTC exemplifies a wider trend.
Tile-based domain-specific languages such as Triton and NVIDIA's cuTile are attracting substantial commercial investment through their role in neural network training.
The common principle is to delegate fine-grained parallelism -- thread mapping, vectorization, specialized matrix units -- to the compiler, leaving the developer free to concentrate on operation fusion and software pipelining.
Matrix-free finite element kernels, whose inner structure is a sequence of small tensor contractions, fit this division of labour naturally, which is why we consider such toolchains relevant beyond Intel hardware.

\subsubsection{Kernel Specialization and Compilation Trade-offs}

These kernels consist of nested loops with small trip counts, so compile-time loop bounds give the compiler backend considerably more to work with.
D3.2 reported a throughput gain of at least 30\% for the templated BK1 and BK5 kernels.
That figure is a lower bound rather than a characteristic value: the gap to the achievable peak of the device proved larger than the comparison against the untemplated baseline suggested.
For reference, \citet{Kronbichler19} report roughly a factor of three from the same optimization on CPUs, attributing it to complete unrolling of the short inner loops and a better instruction schedule, and likewise find the effect most pronounced at low polynomial degree.
The kernels of this report gain at least as much as those of D3.2.

Two mechanisms are at work, on different architectures.
On Intel GPUs the expected one: with static trip counts the compiler unrolls the loop nest fully and fuses loops into favourable execution patterns.
This is pronounced at low polynomial order but does not carry over to high orders, where the unrolled loop body outgrows what the compiler handles well.
On NVIDIA GPUs, where the kernels are thread-based, a second and more persistent mechanism dominates.
Recovering the tensor-product indices $(i,j,k)$ of a degree of freedom from its linear index requires integer division and modulo, among the more expensive scalar instructions on these devices.
Templating the quadrature point counts makes the divisors compile-time constants, letting the compiler substitute a multiply-and-shift sequence.
Analysis with Nvidia Nsight Compute bears this out: for a variant with two-dimensional thread mapping within the block, kernels with runtime loop bounds issue some 8.8 times as many integer instructions as their statically sized counterparts.

Static specialization therefore pays off for different reasons on different targets; on thread-based kernels the benefit is tied to index arithmetic rather than to a favourable unrolling decision.

Its price is compilation time and library size, both growing with the number of instantiated variants.
So far this has remained acceptable, and the implementations reported here use static templating throughout.
Should the trade-off worsen, several mechanisms retain compile-time constants without instantiating the full variant space ahead of time:

\begin{itemize}
    \item \textbf{CUDA Jitify}, for runtime kernel compilation and caching on NVIDIA hardware.
    \item \textbf{SYCL specialization constants}, for injecting configuration-dependent constants at runtime within oneAPI.
    \item \textbf{TinyTC}, JIT-based by design, generating code specialized to the tensor shapes encountered at execution time -- anticipated in D3.2 as a prospective advantage of a tensor DSL.
\end{itemize}

Others in the community pursue the same goal through domain-specific languages and finite-element-tailored intermediate representations.
A practical constraint here is that Kokkos, on which the portable deal.II kernels are based, offers no such abstraction; for Kokkos-based application codes it may therefore be preferable to fix the polynomial order at build time rather than dispatch on it at runtime.

Which route best suits a general-purpose finite element library remains open, and the answer will likely depend on maintainability and build-system considerations as much as on the performance figures reported here.

\section{Conclusion}
\label{sec:conclusion}

This report has extended the co-design work of D3.2 in three directions.

First, the batched (thread-coarsened) mapping of elements to thread blocks resolves the poor low-order performance identified in the first report.
By assigning several elements per thread block instead of one, the register and shared-memory capacity left idle by the 32-block-per-SM limit is recovered, raising the achieved fraction of the roofline limit from 27\% to 48\% for $p=1$ on the NVIDIA GH200 and delivering a $2\times$ speedup for the Laplace operator.
The same mechanism addresses wavefront underutilization on AMD hardware.

Second, the benchmark suite has been extended beyond the scalar, $H^1$-conforming kernels of D3.2 to the $H(\mathrm{div})$-conforming Raviart--Thomas element family, which is required by mixed formulations of the Navier--Stokes equations.
The vector mass, mixed divergence and mixed gradient operators have been implemented and measured on both NVIDIA and AMD accelerators, and initial implementations targeting NVIDIA tensor cores in FP64 and TF32 are available.

Third, operator evaluation has been embedded in a complete conjugate gradient solver, allowing the gap between kernel-level (BK) and problem-level (BP) throughput to be quantified.
The remaining difference is attributable to gather--scatter overheads and inter-GPU communication rather than to the operator evaluation itself, which confirms that further gains at the application level must come from the solver and communication layers.

The comparison of programming models has been broadened accordingly.
High-level directive-based offloading remains convenient but does not reach machine limits for arithmetically intensive high-order kernels, whereas the tile-based approach represented by the Tiny Tensor Compiler approaches the bandwidth limits of Intel GPUs consistently across polynomial orders.
Static kernel specialization was confirmed to be a significant lever, with just-in-time compilation strategies keeping the resulting build-time cost manageable.

The energy-efficiency measurements reported in Section~\ref{sec:energy} are, at the time of writing, still being extended to the full range of target platforms.
A consolidated assessment of energy efficiency across the benchmark suite and the participating architectures will therefore be presented in the final project report.
